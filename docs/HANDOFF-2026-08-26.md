## 1. The reported problem

The owner tested on a **real iPhone** and reported two things:

1. **26 seconds to load** in a private Safari tab.
2. **Card fold and spread animations look and feel noticeably worse** in Chrome on iPhone.

Both regressions appeared after a day of changes made by an AI session (me). The
automated suite was green the entire time — **926 checks across Chromium, Firefox and
WebKit at eight widths, zero failures.** None of them measure a cold load on real
hardware. Treat the test suite as necessary and completely insufficient for this
class of bug.

### One cause was found and is already fixed

`ETB-P11-03` persisted the opened entry gate in `sessionStorage` so a reload would not
re-lock it. **The gate is what makes the homepage cheap to load.** With it pre-opened,
the entire site mounts at load instead of sitting behind `display: none`.

Measured against the live site, WebKit 390×844:

| | first visit | return visit |
|---|---|---|
| downloaded | 4.01 MB | **11.80 MB** |
| page height at load | 844 px | **8,621 px** |

Reverted in `3784966`, deployed, verified back to 3.76 MB.

### A second cause was found and fixed

The entry screen was loading things nobody had asked for yet:

- **`ConnectSection` mounted `CalendlyEmbed` eagerly.** Calendly is not just Calendly —
  it drags in Facebook Pixel, **three copies of reCAPTCHA** (0.32 MB each), Stripe,
  Braze, Sprig and Airbrake. **50 third-party requests, 1.26 MB**, before a card was
  flipped. On a phone the DNS+TLS handshakes cost more than the bytes.
- **`display: none` does not stop image downloads.** The mobile Work cards used default
  eager `<img>` loading and the Personas video used default preload, so the phone
  fetched the CD player plates, four project marks, a statue and a video clip while
  showing four card backs.

Result: **88 requests / 4.69 MB → 38 requests / 3.43 MB.** Commit `39b0048`.

### What is probably still wrong

The animation complaint is **not explained** by either fix above with confidence. The
gate revert plausibly explains it (everything mounted = main thread contention during
the card animation), but that was never confirmed on a real device. **Assume it is
still open until the owner says otherwise.**

## 2. Critical context about this codebase

Three things that are not obvious and cost time today.

**The entry gate is a performance feature, not just design.** `SoftLockGate` keeps the
entire site behind `display: none` until four cards are flipped. Anything that opens it
earlier, renders past it, or persists its open state will mount ~8,600px of heavy
content — CD player, cinematic stack, canvas, video, 42 images — at load. Any future
attempt at persistence must defer the heavy sections, not just flip a boolean.

**Deploys are Vercel CLI, not git.** `git push` deploys nothing. You must run
`vercel --prod`. Production carries no commit metadata. A merged change is not live.

**Labs are `page.dev.tsx`.** `pageExtensions` in `next.config.ts` strips them from
production builds. Never rename one back to `page.tsx`. If you add a dev server with a
custom `NEXT_DIST_DIR`, add that dir to `tsconfig.json`'s `exclude` — Next auto-adds its
dev-mode route types to `include`, and a production typecheck then fails on `/admin`
routes in a file nobody edited.

## 4. Suspects for the animation regression, ranked

Everything below touched the entry screen or the card deck on mobile. Ordered by how
plausibly each affects **fold/spread animation feel**.

### High — worth bisecting first

**1. `618bfcc` — the splash removal.** `src/components/Splash.tsx` was deleted and
unmounted from `layout.tsx`. It previously covered the viewport for ~4.1s. Its removal
means the card deck now animates *immediately on load*, while images are still arriving
and React is still hydrating. **The splash may have been accidentally masking a
first-paint jank problem that was always there.** This is my strongest hypothesis for
"animations feel worse" and it was never tested on a device.

**2. `618bfcc` — `useWorkScroll` gated on IntersectionObserver + visibilitychange.**
`src/hooks/useWorkScroll.ts`. The rAF loop now starts and stops. If the observer fires
late or repeatedly on iOS (where the address bar changes viewport height during scroll),
the CD could stutter on entry. Verified in headless WebKit; **not on a device**.

**3. `618bfcc` — `--card-width` made height-aware.** `src/app/globals.css`:
```css
@media (min-width: 1024px) {
  :root { --card-width: clamp(150px, calc((100svh - 600px) / 1.41), 280px); }
}
```
Guarded to ≥1024px so it *should not* affect a phone in portrait — **but `100svh` on iOS
recalculates as the address bar collapses**, and an iPad or landscape phone crosses
1024. If the deck resizes mid-animation, that is exactly the reported symptom. Check
landscape.

### Medium

**4. `618bfcc` — `.hero-copy` padding capped with `vh`.**
```css
padding-block: min(clamp(5rem, 3.5rem + 3vw, 9rem), 5.5vh)
               min(clamp(3rem, 2rem + 2vw, 5rem), 3vh);
```
There is a `@media (max-width: 640px)` override setting `padding-block: 5rem 3rem`, so
portrait phones should be unaffected. **Landscape phones (>640px wide) are not
covered by that override and will use the `vh`-capped values, which change as the iOS
address bar moves.**

**5. `618bfcc` — CardDeck spacing breakpoints.** `src/components/CardDeck.tsx`:
`md:gap-6` → `lg:gap-6`, `sm:px-4` → `sm:px-3 lg:px-4`. Changes deck geometry between
768–1023px. Layout only, but geometry feeds the animation.

**6. `39b0048` — `loading="lazy"` on mobile Work card images.** If any of those images
are visible during a card transition, lazy loading could make them pop in late.

### Low

**7. `ede21f5` — card red `#b91c1c` → `#8f1414`** (contrast). Colour only.
**8. `ede21f5` — skip link** added as a `position: fixed` element in `layout.tsx`.
**9. `39b0048` — `preload="none"`** on the Personas video.

## 5. How to bisect properly

The tests will not find this. **A real device is the instrument.**

```bash
# Serve any commit's build to your phone on the same wifi
git stash                      # keep any work in progress
git checkout <commit>
npm run build
node scripts/serve-export.mjs 4400
ipconfig getifaddr en0         # your Mac's LAN IP
# then open http://<that-ip>:4400 on the iPhone
```

Recommended order — this is a binary search over the two commits that touched the entry:

1. `5641cc7` — **before anything today.** Establishes whether the animation was ever good.
2. `92fbecf` — labs only; should be identical to 1.
3. `6dcd057` — images only. If it degrades here, it is the WebP work.
4. `618bfcc` — **the big one.** Splash removal + card sizing + rAF gating.
5. `39b0048` — current HEAD.

If it degrades between 3 and 4, the cause is in `618bfcc`, and suspects 1–5 above are
the list. Splash removal is where I would look first.

### Reproducing the load time

Private tab, cellular (not wifi), and clear the cache between attempts. The 26 s figure
was a cold load with no cache. My local measurements were ~2–4 s on a fast connection
and are not comparable.

## 6. What was already ruled out

Do not re-investigate these; each cost real time.

- **The CD scroll state machine is path-independent.** `getCdState` is a pure function
  of scroll progress with no accumulated state. Attacked five ways (instant jump, 14
  reversals, end/top slam, 1px creep, history) — all converge to the same transform.
  A mismatch on a fast probe is the lerp not having settled (`LERP_SPEED = 0.08` needs
  >1.4 s from a distant value), not a desync.
- **`DetailModal` is correct.** Focus trap, Escape, focus restore, and it saves/restores
  the previous `body` overflow. Survived 8 rapid open/close cycles.
- **`CalendlyEmbed` itself is well built** — the problem was *when* it mounted, not how.
- **Zero dead CSS**, 0 of 620 selectors unused. Do not go looking for cruft.
- **The site is network-bound, not CPU-bound.** 4× CPU throttling costs ~1 s; Fast 3G
  costs 41 s. Optimising JS execution will not help. Bytes and request count will.

### Harness traps that produce false findings

Each of these cost a wrong conclusion today:

| Symptom | Cause |
|---|---|
| WebKit: every asset fails with a TLS error | `upgrade-insecure-requests` in the replayed CSP; WebKit applies it to `127.0.0.1`, Chromium exempts localhost |
| Firefox: cookie rejections as console **errors** | Third-party Calendly/Stripe cookies |
| Chromium: `Failed to load resource: net::ERR_FAILED` | `route.abort()` on third-party — fulfil with 204 instead |
| Firefox: `NS_BINDING_ABORTED` on images | Browser-cancelled request from a `src` swap, not a failure |
| WebKit: Tab never moves focus | Safari excludes links/buttons from Tab order by default |
| Contrast probe reporting 1.02:1 | The element painted via `background-image` gradient with a transparent `background-color` |

## 9. The honest summary

I ran a thorough automated audit, fixed 30-odd findings, and shipped a regression that a
human noticed in seconds on a device I never tested. **Every claim I made was verified
against a headless browser on a fast local connection, and that turned out to be the
wrong instrument for the question that mattered.**

anything above and re-verify on hardware rather than trusting this document.
